# Incus inventory provider: private setup handoff

This is a manual acceptance procedure, not an installed collector. Keep the actual mapping, policy, client configuration, inventory, and change record in the private installation. The public project needs only the reusable procedure and synthetic examples.

1. **Approve declarations (offline).** Trace the instance lists to their consumers at a pinned revision. Confirm server and project with the operator. Preview names and list-derived kinds; include only explicitly declared CPU and memory. Reject duplicate scoped names. Run the CLI with declarations alone, check the rows against the source lists, and record mapping approval privately. `not connected` is expected; approval does not authorize reads.
2. **Provision the identity.** Use the handoff below. Capture the version-specific procedure actually used, not just the proposed configuration.
3. **Accept one scan separately.** Show the operator the source, project, requested reads and effective permissions. After explicit approval, use only the dedicated identity. Retain only name, type, status and `limits.cpu` / `limits.memory` from `expanded_config`; never dump full config into reports. Use the declaration scope and the [scan envelope](examples/complete.json) with the actual attempt time. Mark `complete` only for a successful unfiltered enumeration with verified whole-project visibility and all required records; otherwise record `partial` or `failed`. Run `python3 silentdeluge.py "$PRIVATE/declarations.json" "$PRIVATE/scan.json"`. Compare sourced rows privately, then replay a simulated incomplete attempt after a verified snapshot to check retained evidence. This does not authorize scheduled collection.

## Handoff to the private homelab agent

> Configure a dedicated Incus API client identity for SilentDeluge inventory in the operator-approved server/project. Use the approved private mapping for scope. Your remit is identity provisioning and verification only, not drift collection, guest access or unattended monitoring.
>
> First inspect the installed server version, current authentication and authorization policy, and private change-management conventions. Consult the matching Incus docs ([authentication](https://linuxcontainers.org/incus/docs/main/authentication/), [authorization](https://linuxcontainers.org/incus/docs/main/authorization/)). Preview the exact grants, identity routing, changes, impact on existing clients, and rollback before applying. Reuse existing fine-grained authorization where possible. If this requires a new backend, network exposure, global policy change, or broader permissions, stop and get operator approval. Do not weaken existing access controls.
>
> Use an isolated client configuration and credential, not an admin SSH identity, admin socket, copied admin key, or a new alias for existing admin credentials. Verify server identity. Permit project-wide instance enumeration (including stopped instances) and reads needed for name, kind, runtime status and effective limits. No other projects, writes, lifecycle changes, exec, console, guest files, or probes. A project-restricted TLS certificate alone is **not** a read-only policy. If the installed setup cannot enforce the scope, leave SilentDeluge disconnected and explain the blocker.
>
> Verify the effective policy applies to this identity, not just that a list call succeeds. Use policy inspection or a supported permission evaluator to check prohibited grants; never attempt a mutation, exec, file read, or probe to test denial. Establish that visibility covers the whole project, not just selected instances. If a live read is needed for verification, ask for a one-time read first. Record any unverified property explicitly. Keep provisioning credentials, enrollment tokens, raw configuration, and real inventory out of chat, public Git, and logs.
>
> Leave a private setup record: server version and policy mechanism; approved scope and requested reads; sanitized commands actually applied and policy changes; where the client config is kept (reference only); evidence of allowed reads, denied capabilities and scope completeness, distinguishing observed from inferred; revocation and rollback steps; and remaining acceptance gates. Return only status (ready for one-time read / blocked), a private record location, and the nonsecret client config reference and alias. Do not enable a collector.
